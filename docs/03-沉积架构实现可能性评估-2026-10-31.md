## 0. 一句话结论

**"能不能搭起来"：能。机制层已被两级原型证明，宿主层本轮也拿到了"注入→学到→可截断→可隔离"
的正面实测。真正的缺口不在架构，而在两处工程/算法欠账：①L0 的语言常识（体验层）；
②技能与通用能力的争抢（L1 准入）。前者要换更大基座，后者要 replay 混采——
都不是"再训几步"能解决的，也都不是架构本身的问题。**

其中**最该记住的一条新证据**：本轮首次在 L0 上实测了 L1 沉积物的端到端代价——
技能保真几乎免费（r2 都不掉点），但**通用能力被挤掉 22–34%**。
也就是说：**这套架构在 0.83B 骨干上的瓶颈不是显存、不是体积、不是蒸馏，而是"技能与通用能力的争抢"**。

给三层的判断（理由见 §3–§4）：

| 层 | 判断 | 置信度 | 一句话依据 |
|---|---|---|---|
| 机制层（分频沉积/竞价仲裁/保真门） | **可实现** | 高（80%） | 玩具尺度已跑出税 p95 145→30ms、命中率 0.74→0.96、相图 11/28→22/28〔实测〕；本轮 L0 上也验证了"注入→学到→可截断"〔实测〕 |
| 宿主层（L0 当技能宿主、MSP 的一端） | **成立（D2 双指标过线）** | 中高（70%） | D2 最终：**A_tf 0.973 / A_gen 0.880**（replay 35% × 2500 步）〔实测，§10.7〕；秩截断 r8/r2 保真 0.99–1.01〔实测〕；**唯一残留是 C 门 1.037× > 1.02**（注入代价 -25%→-3.7%，靠 replay 压下来） |

## 1. 方案要什么 vs 我们有什么

方案 §2.1/§4 的锚点是「4B 级稠密 Q4_K_M ≈2.2–2.8GB + 短程神经记忆读出头 <0.2GB」，
即 L0 要有真正的语言与常识能力。我们的 L0 是 **0.828B / fp16 1579 MiB / Q4 约 0.47GB**，
规模是锚点的 1/5，训练量是 Chinchilla 最优的约 1/80。这个差距决定了后面的所有判断。

| 方案部件 | 方案要求（原文） | 现有证据 | 判定 |
|---|---|---|---|
| L0 岩基带 | 4B 级稠密 Q4，承担 attention/路由/常识 | 0.83B，ppl 56.9（同验证集），生成无指令跟随〔实测〕 | ⚠️ 预算极宽裕、能力严重不足 |
| L1 热沉积带 | 0.8–1.2GB，若干 r=8 迷你 LoRA + 记忆槽，由使用自组织 | 6GB 档可留 **4.17GB**（空间过剩：r8 沉积物仅 12.1MiB，1GB 装 84 个）〔实测〕；保真 r8 0.992〔实测〕；**但 C 门 1.33× 不过**〔实测，§3.2〕 | ⚠️ 空间充裕、保真达标、**准入被通用回归挡住** |

## 2. 被证据"杀死"的分支（不需要再花时间）

这三条是原型阶段就诚实地判了死刑的，**不要在本项目里复活**：

1. **多技能加法联合合并常驻**：6 技能 ΔW 直接相加，保真 0.13–0.57〔实测-引用〕→ 必须隔离挂载。
2. **跨技能融合成超级技能**：r16 0.23–0.62，r48+温度 KD 仍 0.41–0.80〔实测-引用〕→ L1 只能"一技能一沉积物"。
3. **PCA 共享码本做 L4 压缩**：行为保真能到 0.98，但码本自带全部方差，648KB→648KB〔实测-引用〕→ L4 只能是检索索引，不是压缩格式。

对评估的意义：**L1 的容量账要按"每个技能一个独立低秩体"算，不能按"合并成一个"算**。
这直接影响 §3.2 的"1GB 能装几个"。

### 2.5 对照方案 §7 的四组验证实验：我们现在跑到哪一步

方案自己定义了验证路线，用它当标尺最公平：

| 方案实验 | 玩具尺度 | 真模型尺度（当前 L0） | 完成度 |
|---|---|---|---|
| 实验1 沉积闭环（蒸馏→保真门→晋升→税下降） | ✅ 已过（税 145→30ms） | 技能注入 ✅、**蒸馏保真本轮实测 ✅**（r2 保真 1.008）、**C 门实测 ❌**（1.22–1.34× vs 1.02 门）、闭环未接线 | **约 60%** |
| 实验2 生成式插件（超网络 prompt→参数） | — | 完全没有 | **0%** |
| 实验3 MSP 迁移（存亡假设） | ✅ b/a=0.94 | 只有表示对齐的旁证（中层 cos 0.974、检索@1 0.09），**E3 协议未搬过来** | **约 20%** |
| 竞价仲裁（方案 §3） | ✅ 相图 11/28→22/28 | **无 KV 页可仲裁**（无 cache） | **约 20%** |

这个视角的结论比"通过/未通过"更有用：**四个部件里没有一个是被证据否掉的，
全部卡在"真模型侧还没接上"**——除了 L4 基因化（已被证伪，需换超网络）。

## 3. 逐部件判定

### 3.1 L0 岩基带：预算宽裕，能力不足（最大缺口）

- 显存账〔实测〕：fp16 去重权重 1579 MiB；6GB 档 @ctx4096 → 权重 1579 + KV 144 + 工作区 150
  = **L1 可留 4.17 GB**。方案只要求 L1 0.8–1.2GB → **预算是需求的 3.5 倍**。
- 更关键的一个账〔实测+算术〕：本模型一个 r=8 LoRA 沉积物只有 **12.1 MiB**
  （24 层 × 7 矩阵 × r=8 × (in+out)）。于是
  **1 GB 能装 84 个、4.17 GB 能装 353 个 r=8 沉积物**（r=2 更小，3.0 MiB）。
  也就是说：**L1 容量在本模型上根本不是约束**——方案担心的"1GB 里挤几个技能"这个矛盾，
  在 0.83B 骨干上直接消失了。约束只剩两处：KV 预算（144MB@4k）与 L0 的能力。
- 能力账〔实测〕：验证 ppl 56.9；生成样本是无指令跟随的统计性续写
  （「人工智能的核心挑战在于」→「,在"互联网+"时代,…」）。方案要 L0 干的
  "attention + 路由 + 常识"里，**前两项是结构性的（GQA/KV 记账/hidden 可取，已验），
  第三项完全没有**。
- 判断〔判断，置信度高〕：把 L0 当"宿主"可以，当"脑"不行。要让 L0 直接对用户产生
  可接受的回答，需要**换更大的基座，或再烧 50–100 倍 token**，不是调架构能解决的。

### 3.2 L1 热沉积：保真几乎免费，但"通用伤害"才是真门槛

本轮在 L0 上首次端到端测了「训练技能 LoRA → 秩截断 → 复测行为与通用 ppl」〔实测，§9〕：

- **保真门（技能能力）**：r=16 教师 A_tf 0.727 → **r8 0.722 / r4 0.722 / r2 0.733**。
  保真率 0.992 / 0.992 / 1.008 —— **截到 r=2 都不掉点**，而 r=2 只有 3.0 MiB。
- **C 门（通用回归，98k token 验证集）**：裸基座 ppl 56.92 →
  r16 **76.17（1.338×）** / r8 75.70（1.330×）/ r4 74.04（1.301×）/ r2 **69.32（1.218×）**。
  门限是 1.02，**全部不过，连 r2 都差 20 个百分点**。
- 结论（这是本轮最重要的一条架构结论）：
  **在 0.83B 骨干上，L1 的死穴不是"沉积物装不下/保不住"，而是"技能一进去就把通用能力挤掉"**。
  缩小秩能减轻伤害但救不回来（1.34→1.22×）。
- 由此可以立刻改写方案的一条实现约定：**L1 的"常驻"必须定义为"驻留显存但隔离挂载"
  （用到才 merge、用完 restore），不能定义成"合并进 L0 常驻"**。
  这正是玩具 E1d 采用的政策，现在在真模型上有了量化理由（合并常驻 = 永久 -25% 通用能力）。
- 附带的方法学教训〔实测〕：单段 ppl 给出的退化是 1.043，98k token 验证集给出 1.338。
  **单段落 ppl 严重低估伤害**，C 门必须用验证集口径。

### 3.3 L2/L3 与加载税：机制已被证明，只差接线

玩具尺度的核心数字〔实测-引用〕：200 轮 Zipf 负载下常驻命中率 0.74→0.96、
加载税 p95 **145→30ms**、任务分不降反升（0.262→0.282）。这个结论的前提是
"插件能被蒸馏成更小的常驻体"，而 §3.2 正是这个前提在真实骨干上的检验。

对 6GB 档的真实意义：加载税 30ms 相对 prefill 已经是噪声级；Node 端的端到端时序
（300MB 冷插件 670ms TTFT，被 prefill 隐藏）说明**这条路的天花板不在调度，在带宽**〔实测-引用〕。

### 3.4 竞价仲裁：设计完备，但被"没有 KV cache"卡住

仲裁的对象是"KV 页 vs 插件"。而当前 `SedimentBase` **没有 `past_key_values`**，
每 token 全序列重算〔实测：32 tok 2723ms〕。没有 KV 页，就没有可报价、可驱逐的租户，
仲裁器在 L0 上是空转的。这是**架构落地的前置工程缺口**，不是研究问题。

### 3.5 MSP 跨骨干：在真骨干对上**不成立**，且失败原因已量化

玩具尺度报 b/a=0.94（同架构同深度的两个小骨干，键是近乎正交的单 token 置换）。
本轮第一次在真骨干对（Qwen2.5-3B / 36 层 / d=2048 → 自制 L0 / 24 层 / d=1536）上按
方案 §7 实验 3 的协议重做〔实测，`scripts/e3_msp_real.py` + `e3_msp_split.py`〕：

| 臂 | 准确率（47 类寻址，机会 0.021） |
|---|---|
| a 联合上限（在 L0 本地坐标训） | **1.000**（槽容量不是瓶颈） |
| Qwen 本地（参考骨干自用） | 1.000 |
| **b ISA 转译**（Qwen 训键 + 同分布锚点标定 → L0 寻址） | **0.000 / 0.043** |
| b0 不转译（随机投影直读） | 0.029 / 0.043 |

**b ≈ b0 ≈ 机会水平**：标定后的键与随机投影的键一样没用，转译没有带来任何信息。

**为什么**（这是本轮最硬的一条量化结论）：把"类间夹角"和"标定误差夹角"放在一起看——

| 量 | 值 |
|---|---|
| 不同 prompt 的 hidden 类间平均余弦 | Qwen **0.974** → 类间夹角 **13.2°** |
| 标定图在评测集上的保真度 | 余弦 0.964–0.979 → **误差夹角 11.7–15.4°** |
| 误差/类间 夹角比 | **≈ 0.9–1.2** |

判别上限要求"误差夹角 ≲ 类间夹角的一半"，这里误差和类间**一样大**，所以无论用什么线性标定
都不可能区分类别。玩具为什么能到 0.94？因为玩具的键是近正交的（类间夹角 ≈ 90°），
10° 的标定误差完全可以容忍。**MSP 的可行性不取决于标定算法，而取决于
「类间夹角 ÷ 标定误差」这个信噪比**；真实骨干上这个比 ≈ 1，玩具上 ≈ 0.1。

**要紧的副产品**：同一条骨干对，锚点换成**同分布**文本时标定余弦 0.977，
换成 200 条通用语料窗口则掉到 0.640（检索@1 = 随机）。
**锚点分布比锚点数量重要**——这解释了为什么玩具的锚点漂移曲线（4→0.10 … 48→0.96）
在真骨干上复不出来：它测的是"同分布锚点的数量效应"，不是"任意锚点的覆盖效应"。

**结论**：MSP 在 3B↔0.83B 这对骨干上**不成立**。要提高信噪比只有两条路：
① 把标定误差从 12–15° 压到 ≤3°（cos ≥ 0.999，需要逐层标定 + 非线性探针，难度高）；
② 降低对精度的要求——把记忆槽绑到**更长的语义单元**（段落级/答案集级），让类间夹角从 13° 拉开。
在此之前，方案 §2.3 的"跨骨干知识包市场"应按"同族/同架构"收缩，这与玩具报告 §7 给出的
诚实收缩方向一致，但阈值更严：**不是"差 1 个点"，而是差一个数量级。**

### 3.6 L4 基因化：维持"已证伪"

玩具已判：PCA 码本零压缩。方案要的"真超网络（prompt→参数）"在本项目里**一行代码都没有**，
且它本身就是独立研究项。评估结论：**L4 在本轮可行性判断中按不存在处理**，
不影响 L0–L2 主体。

## 4. 绑定性约束排序（决定"能不能用"的三个量）

按"修起来最便宜 / 影响最大"排序：

1. ~~KV cache~~ **已完成（2026-10-31 凌晨）**，但结论与预期不同：正确性全部通过
   （训练 loss 逐位一致、解码逐 token 相同），**速度几乎没变**（93→91 ms/token）。
   profiler 显示 GPU 只花 8.8ms，CPU 花 142ms（169 次 `aten::mm` 每次 134µs 调度），
   且 T=1 与 T=40 的 forward 同为 ~86–92ms —— **本机瓶颈是逐算子调度，不是重算**。
   真正的提速手段是**批量生成**（左填充，实测 **7.7×**）与算子融合，见 §10。
2. **通用能力的挤占（算法，未知工期）**：L0 上挂一个技能就让通用 ppl 涨 22–34%〔实测〕，
   而 L1 的准入线是 1.02×。**这是目前唯一"已知会挡住架构落地"的量**，
   且继续训练会加重它（训得越熟，挤占越狠），方向性解法只有：混采 replay、
   限制注入范围（更少层/只注入 qkvo）、或维持隔离挂载。
3. **技能训练量（算力，2–6 小时/轮）**：决定 D2 能否过线，见 §5。
4. **L0 语言能力（算力，45 小时/epoch 起）**：决定"体验层"能否成立。**不建议现在做**，
   理由见 §5.3。

## 5. 继续训练能买到什么

要区分两条完全不同的训练轴，它们的成本与收益差一个数量级：

### 5.1 两条轴的对照

| 轴 | 做什么 | 成本〔实测/推算〕 | 买到什么 | 建议 |
|---|---|---|---|---|
| A. 技能训练（LoRA on L0） | 在现有 L0 上继续训 Sedu 技能 | 2.9 s/步（bs4）→ 1000 步 ≈ 48 min | A_tf 从 0.823 往 0.9+ 推；A_gen 从 0.32 往 0.5–0.7 推 | **先加 replay 混采再训**（否则 C 门继续恶化） |
| B. 预训练续训（backbone） | `--resume` 跑满 1 epoch | 4.4k tok/s → 88.6k 步 ≈ **45 h** | ppl 56.9 → 约 35–45〔推算〕；语言更顺，技能学得更快 | **不做**（见 5.3） |

### 5.2 轴 A 的外推：能买到什么、买不到什么

实测曲线（同一协议，bs4，LoRA r16）〔实测〕：

| 步数 | 样本通过数 | A_tf | A_gen |
|---|---|---|---|
| 0（裸基座） | 0 | 0.174 | 0.000 |
| 150 | 600 | 0.504 | — |
| 300 | 1,200 | 0.580 | 0.020 |
| 900 | 3,600 | 0.823 | 0.320 |

两条经验事实：

- **A_gen ≈ A_tf^5.85**，反解出的指数 5.85 与 Sedu 答案平均 token 数 5.8 几乎相等〔实测〕。
  也就是说"生成对"要求"逐 token 几乎全对"，这不是模型缺陷，是**任务结构**。
- 因此预注册线 A_gen≥0.80 等价于要求 **A_tf ≈ 0.963**。而 A_tf 0.95 时 A_gen 只有 0.74。
- 换句话说：**继续训练能把 A_tf 推到哪，决定 A_gen 的天花板；但 0.80 这条线
  靠"训得更久"达到的性价比极差**（见下）。

步数需求外推〔推算，标注不确定性〕：
- 最近窗口（300→900 步）每 600 步涨 0.243 ≈ **每千步 +0.40**；按此外推
  A_tf 0.90 在 **约 1.1k 步**、0.96 在 **约 1.25k 步**（偏乐观，忽略饱和）。
- 用饱和曲线拟合（A_tf = A∞ − (A∞−0.174)e^(−n/τ)）得 A∞≈0.85、τ≈275，
  **反而判定 0.90 不可达**（偏悲观，4 个点定 3 个参数，不可信）。
- 两个外推给出相反结论，说明**只有 3 个数据点，任何曲线拟合都是过度解读**。
  诚实的工程口径：**0.90 大概率在 1200–2000 步（1–1.6 h）内出现；0.96 需要 2000–4000 步
  （1.6–3.2 h），且不保证。**

同类对比（同管线同数据，最硬的一条）〔实测〕：Qwen2.5-3B-Instruct 用 **bs16 × 3 epoch
= 14,400 样本通过**拿到域内 acc **1.000**；L0 用 3,600 通过只拿到 A_gen 0.32。
按 §5.2 的外推，L0 要把 A_tf 推到 0.96（A_gen 0.80 的前提）约需 8,000–16,000 样本通过
——**样本量级与 3B 相当，终点精度却更低**。这就是 0.83B 与 3B 的差距在同一个任务上的直接投影，
也解释了为什么"继续训"对 L0 的边际收益比 3B 差。

### 5.3 轴 B（预训练续训）为什么现在不建议花这 45 小时

1. **不改善验收**：D1 已 ✅（ppl 门槛是"远优于随机"），续训买的是"语言更顺"，
   不买 D2 的过线能力。
2. **不改善架构可行性**：架构的三个创新点（沉积/仲裁/MSP）都不依赖 ppl 从 57 降到 40。
3. **性价比被轴 A 碾压**：45 h 换 ppl 降 20 点（且不可验证外推），vs 2–6 h 换 D2 过线。
4. **真正需要的是规模而不是 token**：0.83B 的天花板在那里，把 0.19B token 训到 0.9B
   token 仍然是"小模型"，方案要的 4B 级常识能力不可能靠续训补出来。

**结论**：续训只有在"决定把 L0 路线当产品主线"时才值得，那是另一个决策
（届时更该做的是换基座：Qwen2.5-0.5B/1.5B 在这台机器上 ppl 会低一个数量级，
代价是放弃"全自制"）。

## 6. 继续训练买不到、甚至会变糟的事

> **先说最反直觉的一条**：继续训练技能**会让 C 门更难过**。本轮 600 步时通用 ppl 已 +33.8%，
> 训得越熟 → 技能挤占越强。所以"多训几步把 D2 打过去"这个动作，**代价是通用能力进一步下降**，
> 而 L1 的晋升门恰恰卡在通用回归上。这是一个必须用 replay 混采解决的问题，
> 不是靠加步数能绕过的。

另外四件事，继续训练也买不到：


1. ~~KV cache~~：**已经做了**（§10.1），而且证明它不是你等的那块表——
   本机解码慢的原因是 CPU 调度而非重算，真正的提速手段是批量（7.7×）。
2. **解码约束**：A_gen 的天花板由 A_tf^5.8 决定，训不动。Sedu 是**80 词封闭词典** +
   三种固定问句模板，约束解码（前缀树/词典掩码）能消掉"格式错、复读、编造 token"这类错误
   ——本轮 900 步样本里确实存在（如「鱼和鱼\n鱼\n鱼…」的循环）。
   **但要诚实**：样本里同时存在"选错词"类错误（「miga ve xe fubo ne」应为「mora …」），
   约束解码对它**无效**。所以约束解码是**必要条件而不是解药**，能拿回多少必须实测，
   不能拍脑袋说"拉到 0.8"。
3. **MSP 的身份还原**：这是标定/表示问题，加训练步数无用（本轮 D3 已示警）。
4. **L4 基因化**：需要真超网络，属于独立研究项。

## 10. 执行记录（2026-10-31 凌晨 02:00–03:30）

用户指示"你来执行"，按 §7 的性价比顺序落地，结果如下（脚本与数据都在
`Qwen-work-1/蒸馏实验/scripts/` 与 `l0_acceptance/`）。

### 10.1 KV cache：实现完成，正确性三重验证通过，但**本机不提速**

改动（`model_l0.py`）：`rope_cache` 加 offset、`Attention` 走 `Cache.update(k,v,layer_idx)`、
`Block` 透传、`hidden_states/forward` 接受 `past_key_values`、`prepare_inputs_for_generation`
在有 cache 时只喂最后一个 token、声明 `_supports_cache_class=True`
（transformers 5.8 已移除 tuple cache，只能用 Cache 实例）。

守卫脚本 `diag_cache.py` 三项全过〔实测〕：

| 检查 | 结果 |
|---|---|
| 训练路径不变（同 batch loss，对照打补丁前的模块） | 10.73339176 vs 10.73339176，**差 0.00e+00** ✅ |
| 解码等价（cache vs 无 cache，12 token） | **逐 token 完全相同** ✅ |
| 速度（32 token） | 无 cache 2978ms → 有 cache 2915ms，**基本没变** ❌ |

**为什么没变快**：profiler 显示单次 forward 的 CUDA 时间只有 **8.8ms**，CPU 侧 **142ms**；
169 次 `aten::mm` 每次 CPU 调度 **134µs**（正常 5–10µs）。且 T=1 的 forward 是 86ms、
T=40 也是 92ms —— **成本与序列长度无关，全是逐算子调度开销**。
所以 cache 对"本机 + 0.83B"这个组合几乎无感（对 4B + 6GB 笔记本档、以及 KV 竞价记账才有意义）。

### 10.2 真提速手段：左填充批量生成，7.7×

同一批 8 条 prompt，20 token 生成〔实测〕：

| 方式 | 每样本耗时 |
|---|---|
| 逐条 | 1707 ms |
| 批量 bs8（左 pad + attention_mask） | **223 ms**（**7.7×**） |

代价：8 条里 3 条在 20 token 后与逐条结果分歧（fp16 批量核的数值差，前 8 token 全同）。
结论：**批量评测可用，但要标注"非逐位可复现"**；需要严格复现的单点实验仍走逐条。

### 10.3 错误类型拆分：A_gen 的失败 73% 是"换行复读"，不是"选错词"

用 E1 的 `adapter_sedu_r16`（600 步纯技能，A_tf 0.727）跑 30 条 holdout〔实测〕：

| 类型 | 条数 | 占比 |
|---|---|---|
| PASS（精确命中） | 8 | 26.7% |
| LOOP（换行/片段重复） | 22 | **73.3%** |
| 纯语义错（格式正常选错词） | 0 | 0.0% |
| 生成即 EOS | 0 | 0.0% |

关键细节：**"只在第一个换行处截断"的准确率只有 0.200，比原始 0.267 还低**——
说明现在的 PASS 里有一部分是"复读串里恰好包含正确答案"蹭到的。

**这条数据推翻了我上一轮的建议权重**：约束解码能消掉换行复读（输出变干净、评测变可测），
但**在 600 步这个成熟度上拿不回精度**（首行口径 0.20 就是天花板附近）。
真正的提分杠杆仍然只有 A_tf —— 与 §5.2 的 `A_gen≈A_tf^5.8` 完全一致。

⚠️ **但这个结论随模型成熟度翻转**（2000 步复测，见 §10.6）：同一套"截断"操作在
A_tf 0.939 的权重上把 A_gen 从 0.333 拉到 **0.780**。
所以正确的表述是：**先训到 A_tf≥0.93，再上解码约束**——顺序反了会得出"约束没用"的错误结论。

### 10.4 replay 混采：C 门从 1.338× 救到 1.038×，技能保持 91.4%

同 600 步 / bs4 / r16，唯一变量 = 每步 20% 概率抽一条通用中文（256 token，纯 LM 目标）〔实测〕：

| 变体 | A_tf | A_gen | 通用 ppl（98k token） | C 门 1.02 |
|---|---|---|---|---|
| 纯技能（E1） | 0.727 | 0.267 | 1.338× | ❌ |
| **+ replay 20%** | **0.665** | 0.167 | **1.038×** | ❌（差 1.8%） |

- 技能保持率 0.914（预注册 ≥0.90 可接受）✅
- C 门改善 **0.30**（1.338→1.038），方向完全确认：**挤占是可以用混采换回来的**。

**加跑 35% 混采 × 900 步（把技能样本量补回基线水平）后，两个指标一起变好**〔实测〕：

| 变体 | 技能样本通过 | A_tf | A_gen | 通用 ppl | C 门 |
|---|---|---|---|---|---|
| 纯技能 600 步 | 2,400 | 0.727 | 0.267 | 1.338× | ❌ |
| replay 20% × 600 步 | 1,920 | 0.665 | 0.167 | 1.038× | ❌ |
| replay 35% × 900 步 | 2,340 | 0.744 | 0.333 | 1.030× | ❌ |
| **replay 35% × 2000 步** | 5,200 | **0.939** | **0.780**※ | **1.032×** | ❌（超 1.2%） |

※ 2000 步这一行的 A_gen 是修掉 EOS bug 后的读数（0.333→0.780），详见 §10.6；
同一权重、同一数据、只改 `eos_token_id` 一个参数。

结论（这条比"救回多少"更重要）：**只要把技能样本量补回去，混采不伤技能**——
A_tf 0.744 甚至略高于纯技能的 0.727，A_gen 也从 0.267 升到 0.333。
也就是说 **replay 是近乎免费的正则**，代价只是训练时间（900 步 vs 600 步，~37 min vs ~25 min）。
剩下的 1%（1.030× vs 门限 1.02）建议按以下顺序处理，而不是继续加混采：
① 把 1.02 门在小骨干上重标（0.83B 付 3% 通用 ppl 换一个完整技能，本身是合理交易）；
② 或再抬到 45–50% 混采 + 1200 步，预期能压进 1.02，但技能样本量要同步补。

### 10.5 C 门已并入 D2 判分

`accept_l0_d2.py` 现在输出 `c_gate{bare_ppl, skill_ppl, regress, pass}` 与
`promotable_to_L1`（= D2 过线 ∧ C 门过线）。判分口径写进 docstring：
**通用 ppl 必须用验证集 98k token，禁止单段落**（单段会把 1.338 测成 1.043）。

### 10.6 第四个 bug（B4）：EOS 配置缺失，把 A_gen 系统性压低

2000 步跑完时 A_gen 只有 0.333，但错误拆分显示 **首行准确率 0.800**——模型答对了，
只是不停。查下去发现两件事叠在一起：

1. 本模型的 `generation_config.json` 是**全 None**（`diag_gen2.py` 早期就打印过，当时没往这里想）；
2. `generate` 因此只认 `<|endoftext|>`(151643)，而对话模板的回合结束符是 `<|im_end|>`(151645)。

于是模型答完正确答案、发出 `<|im_end|>`、再生成下一轮答案，整串 exact match 必然失败：

| 配置 | A_gen | 平均输出长度 |
|---|---|---|
| 只认 151643 | 0.333 | 36.0 字符 |
| **151645 + 151643** | **0.780**（30 条口径 0.800） | **7.7 字符** |

同一条权重、同一批数据，**只改 `eos_token_id` 一个参数，A_gen 翻 2.3 倍**。
`gen_rows()` 已永久修正（`accept_l0_d2.py`，注释里写清了原因）。
**教训**：自定义架构 + 空的 generation_config = 生成的停止条件完全靠调用方显式指定；
以后所有评测脚本都必须在 `generate(...)` 里写死 `eos_token_id=[151645,151643]`。

### 10.7 D2 最终位置（replay 35% × 2500 步 + EOS 修复）——**两条主指标都过线**

| 指标 | 读数 | 预注册线 | 判定 |
|---|---|---|---|
| A_tf | **0.973** | ≥0.90 | ✅ |
| A_gen（50 条 exact match） | **0.880** | ≥0.80 | ✅ |
| C 门（通用 ppl 回归） | **1.037×** | ≤1.02 | ❌ 超 1.7% |

曲线（同配置）：1000 步 0.785 → 1500 步 0.870 → 2000 步 0.939 → 2500 步 **0.973**；
A_gen 同步 0.333（EOS 未修时）→ 0.780 → **0.880**。

**这是本项目第一次把"L0 能承载技能"从推测变成过线的实测**：
0.83B 骨干 + 单个 r16 技能 + 30% 的通用混采，2500 步（约 1.8 h）后
holdout 逐 token 准确率 0.973、整句精确匹配 0.880。

剩下的唯一阻塞是 **C 门 1.037×**——注意它是 **L1 晋升门**，不是 D2 判分线。
两个判定必须分开说：**D2（中心模型职责）✅ 通过；L1 晋升（把技能常驻进 L1）仍被 C 门挡**。
而 C 门这条线本身建议重标（§10.4 的论证 + 现在 1.337→1.037 的改善幅度）。
